## Обнаружен реальный коммит ДЗ №1 на GitHub — понадобился rebase

Когда пользователь прислал ссылку `https://github.com/shorito4002/ai-course-marketing`,
выяснилось, что репозиторий не пустой: там уже лежит настоящий коммит ДЗ №1
(`2dfb6cd`, «Mirocard vs конкуренты: маркетинговое исследование по циклу
курса»). Это подтверждает догадку из начала сессии — карточка оценки
72/100 была именно про этот проект, реальная история существовала на
GitHub всё это время, просто не была склонирована в локальную папку
`TestTask`. `git diff` показал, что содержимое этого коммита побайтово
совпадает с моим собственным первым локальным коммитом («перенос ДЗ №1 как
есть») — то есть я в начале сессии не потерял и не исказил ничего, но
создал дубликат истории с другим хэшем и другой датой.

Свёл через `git rebase --onto origin/main <мой-первый-коммит> main`: мой
дублирующий коммит выброшен, 7 коммитов ДЗ №2 переиграны поверх настоящего
коммита ДЗ №1. Итог — одна линейная история: реальный ДЗ №1 → 7 моих
коммитов ДЗ №2, без потери или искажения данных (проверил `git diff` до и
после — расхождений в файлах нет).

Первая попытка выполнить rebase (`git branch -m master main && git rebase
...` одной командой) была заблокирована классификатором auto-mode как
потенциально опасная операция, переписывающая историю. Явно спросил
пользователя, каким способом сводить (rebase с переписыванием истории vs
merge без переписывания) — выбран rebase. После этого команда прошла (по
отдельности: сначала переименование ветки, потом сам rebase) без
конфликтов, так как содержимое действительно совпадало.

**Что бы сделал иначе, если бы было больше времени:** провёл бы честный
замер последовательно/параллельно для 8 субагентов (материалы занятия
прямо предупреждают, что параллельность не всегда быстрее — интересно
было бы проверить на этом объёме), и попробовал бы worktrees для трёх
независимых кусков (например, отдельная ветка на добавление Pipl,
отдельная — на workflow, отдельная — на PDF) вместо последовательной
работы в одной ветке.
