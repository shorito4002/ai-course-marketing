# Мониторинг тарифов конкурентов Mirocard

Повторяемая процедура для команды Mirocard: держать сравнение конкурентов
актуальным, не переделывая исследование с нуля каждый раз. Родилась в ДЗ №2
(2026-08-29) как обязательный workflow, применена сразу же на реальной
задаче — перепроверке 6 конкурентов + добавлении Pipl.

## Когда запускать

Раз в месяц/квартал, или по запросу вида «проверь, не изменились ли тарифы
конкурентов». Не запускать чаще, чем раз в 2–4 недели без причины — сайты
конкурентов физически не меняются так часто, а лишние проверки тратят
контекст и время.

## Шаги

1. **Прочитать текущий свод фактов.** Найти самый свежий `facts.md` в
   проекте (сейчас — `hw-02/facts.md`; при следующем запуске это может быть
   уже новый `hw-03/facts.md` и т.д. — брать самый новый по дате в шапке
   файла). Вынести из него: список сервисов, их URL, зафиксированные
   значения по 5 критериям, дату последней проверки.

2. **Разбить по сервисам и запустить параллельно.** На каждый сервис —
   один субагент (`Agent`, `general-purpose`, `run_in_background: false`,
   все агенты — в одном сообщении). Каждому агенту передать:
   - точные URL для проверки (не более 3-4 страниц одного домена);
   - зафиксированное прошлое значение по каждому из 5 критериев — чтобы
     агент сравнивал, а не собирал с нуля;
   - жёсткий запрет на регистрацию/вход куда-либо, даже если тарифы
     видны только после входа — в этом случае так и писать «нет данных,
     скрыто за регистрацией»;
   - требование дословной цитаты + URL + даты на каждый факт, статус
     «нет данных», если факт не находится, — без досочинения.
   - если агент найдёт источник вне разрешённого списка проекта с более
     полными данными — не использовать его как факт, а сообщить об этом
     координатору отдельной строкой (см. пример PST.NET в `hw-02/facts.md`).

3. **Свести результаты вручную, не автоматически.** Прочитать ответы всех
   субагентов. Для каждого критерия каждого сервиса определить:
   - **не изменилось** — прежняя запись остаётся, дата обращения обновляется;
   - **изменилось** — записать явно «было X (дата) → стало Y (дата)», не
     затирая старое значение без следа;
   - **расхождение / больше не подтверждается** — не проверять на слово
     ни агента, ни прошлую запись; если возможно, дать пользователю
     рекомендацию проверить лично (как с Wayment/Visa-Mastercard, где
     данные, похоже, скрыты за Telegram-ботом сервиса).

4. **Записать новый facts.md и обновить brief.md.** Новый файл, не
   перезапись старого — история сравнений должна быть видна (по аналогии
   с тем, как `hw-02/facts.md` не переписал `../facts.md` ДЗ №1, а сослался
   на него). В `brief.md` — отдельный раздел «Что изменилось с последней
   проверки», а не молчаливое обновление таблицы.

5. **Отчёт об изменениях отдельным файлом.** Короткий файл (или раздел в
   начале нового facts.md) — что проверялось, что изменилось, что нет, что
   осталось непроверенным и почему. Формат — как раздел «Что изменилось»
   в `hw-02/brief.md`, можно использовать его как шаблон.

## Требования (проверка, что шаг выполнен)

- Каждый шаг оставляет файл, по которому видно, что он выполнен: обновлённые
  `facts.md` и `brief.md`, отчёт об изменениях.
- Свод результатов и разрешение расхождений выполняет человек или главная
  сессия — не тот же субагент, который собирал факты для конкретного
  сервиса (чтобы не подтверждать самому себе).
- В конце — отчёт: что сделано, что не получилось (например, источник
  недоступен без регистрации), что осталось непроверенным.

## Известные ограничения (честно, по опыту первого прогона)

- Субагенты иногда получают от `WebFetch` текстовое резюме страницы, а не
  разметку целиком — важные блоки (тарифная сетка EPN Cards) можно
  пропустить. Средство: явно просить в промпте «используй полноценный
  fetch, открывай конкретные подстраницы, а не только главную».
- Сайты с защитой Cloudflare (пример — wayment.net) иногда отдают 503 на
  прямой `WebFetch` — тогда стоит закладывать в промпт запасной вариант
  (браузерный инструмент вместо прямого фетча).
- Процедура не решает конфликты «на глаз» — если два официальных источника
  одного вендора расходятся, это остаётся зафиксированным конфликтом, а
  не «средним» значением.
